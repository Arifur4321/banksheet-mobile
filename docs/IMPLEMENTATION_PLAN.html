01Direct answers to your questions

Your questionAnswer
Can we use the same DB? Yes — and you should. One MySQL database docuflow, one set of users / companies / documents tables, one account that works on web and mobile. But the Flutter app must never open a MySQL connection. It talks HTTPS to the same Laravel app, which owns the database. Full reasoning in §4.
Does the Laravel side need changes? Yes — additive, plus four behaviour-preserving refactors. The web app today has exactly one auth guard (web, session driver) config/auth.php:40-45 and no JSON representation of any screen's data. A mobile app cannot use cookies and CSRF tokens, so it needs a token guard and a new route file. No policy, no migration and no business rule changes. Four existing controllers get logic extracted into services so both clients call one implementation — no behaviour change, and the existing 503 tests are the regression check. See §5.
Can I ship to Play Store and App Store? Yes. Nothing in the product is disallowed. Two hard dates and one hard rule apply: Play requires target API 36 by 31 Aug 2026; a personal Play account created after 13 Nov 2023 must run a 12-tester / 14-day closed test before production access; Apple requires in-app account deletion (the web flow exists at ProfileController.php:43-59, though only $user->delete() is directly reusable — the other four statements are session-bound). Checklists in §12 and §13.
IAP for iOS + Android, Stripe stays on Laravel? Workable, and the design is in §8. The important part: store subscriptions and Stripe subscriptions must resolve into one entitlement. Your plan limits are already centralised in PlanCatalog::applyToCompany() PlanCatalog.php:92-111, so Apple/Google become a third writer into that same function. You must also block double-billing: never let a company hold a Stripe subscription and a store subscription at once.
Feature parity with the website? Realistic in three releases, not one. Most of the 19 sidebar destinations are forms and tables and port cleanly. Four are canvas-heavy (Konva + pdf-lib + pdf.js + interact.js) and genuinely expensive to rebuild natively — the Advanced PDF Editor, Barcode Studio, signature-field placement and on-device signing — plus two TinyMCE screens with no good mobile equivalent. Scope table in §10.
The single biggest thing this plan is about
BankSheet Pro is a server-rendered Blade application. There is some first-party JSON — eight endpoints that your own JavaScript calls with fetch() (PDF-editor save/assets/export routes/web.php:508-511, barcode-studio save/generate :522-523, the guest barcode equivalents, extraction-profile preview :489, PDF-tool status :553, and api-docs/openapi.json) — but every one of them is a narrow action helper for a single canvas screen, not a data API. No screen's data is available as JSON: not documents, not transactions, not the dashboard, not billing, not the team. Every one of those is HTML rendered by PHP. So the mobile project is not "80% Flutter, 20% backend". It is roughly 45% new Laravel API work, 55% Flutter. Plan and staff accordingly.

Non-negotiable principles

  1. One source of truth for business rules. Every mobile endpoint delegates to the same service class the Blade controller uses. If a quota rule changes, it changes in PlanEnforcementService once and both clients get it.
  2. Mobile controllers are thin translators. They validate, call a service, and shape JSON. No if that exists nowhere else.
  3. Additive only. No existing route, controller, migration or view is edited. The 503 existing test methods must stay green untouched.
  4. The device is never trusted. Not for quotas, not for plan state, not for purchase receipts, not for tenant scoping.
  5. The API is versioned and the client is version-gated from day one, so you can force-upgrade old installs. SEO-BankSheet already has this pattern (X-BankSheet-SEO-Client → 426) — and it also has the trap where the config default is 1.0.0 (config/seo.php:165) while the shipped extension is 0.2.0, so every request that does send the header is 426'd. Copy the mechanism, default the version to 0.0.0.

04Can we use the same database?

Yes. One database, one account, one truth. A user who registers on the phone can log in on banksheet.pro the same minute, sees the same documents, the same team, the same plan and the same monthly counters — because there is literally one users row and one companies row.

The distinction that matters is how the app reaches it.

ApproachVerdict
Flutter → MySQL directly
(a Dart mysql client on the device)		 NEVER DO THIS Six independent reasons, each fatal on its own:
  1. The DB username and password would ship inside the APK/IPA. Both are trivially unpackable. That is your production database credential handed to anyone who downloads the app.
  2. MySQL port 3306 would have to be open to the public internet.
  3. All 12 policies and the visibleTo() tenant scope live in PHP. A raw SQL client bypasses every one of them — any user could read every company's bank statements.
  4. Quota enforcement, Stripe reconciliation and the extraction queue are all PHP. Rows inserted from a phone would never be processed.
  5. You could never change the schema again without breaking installed apps you cannot force-update.
  6. It would fail App Store review under Guideline 5.1.1 and Play's data-safety rules.
Flutter → Laravel HTTPS API → MySQL THE PLAN The app holds a per-user, revocable, short-lived token. Laravel resolves the user, applies the same policies and tenant scope, enforces the same quotas, and returns JSON. The database credential never leaves your VPS. This is what "using the same DB" means in practice, and it is what every SaaS mobile app does.
A second database for mobile DO NOT You would immediately own a two-way sync problem across users, companies, documents, quotas and subscriptions. There is no upside.

07Authentication design

You asked for "Flutter authenticates with the Laravel DB, update Laravel just for the Flutter-side login/register, keep all business logic in Laravel". That is exactly what this is.

Why rotation with reuse detection matters

If a refresh token is ever presented twice, that means either a bug or a stolen token. The server marks the chain compromised and revokes every descendant, forcing a fresh login. Your SEO-BankSheet implementation already does this — and its handover notes record a real bug found in testing: revoking inside the transaction meant the subsequent throw rolled the revocation back and the attacker kept working tokens. HANDOVER.md:222-227 Revoke after the commit. Port the fix, not just the feature.

Google Sign-In and Apple's Guideline 4.8 — read this before you build the login screen

Recommendation: ship v1 on iOS with email + password only
App Store Guideline 4.8 requires that an app using a third-party or social login service to set up or authenticate the user's primary account also offer an equivalent option whose login service limits collection to name and email, lets users keep their email private, and does not collect in-app interactions for advertising. In practice reviewers expect Sign in with Apple whenever Google Sign-In is present.

Your web app already offers Google Auth/GoogleAuthController.php. If you put that button in the iOS app, budget for Sign in with Apple in the same release — including the server side, where Apple returns a private relay address and, on some flows, no name at all after the first authorization.

Cheapest correct path: v1.0 = email + password on both platforms. v1.1 = Google on Android + (Google & Sign in with Apple) on iOS. This removes a whole class of review risk from your first submission.

Email verification

Today verification is implemented but enforced nowhere — User does not implement MustVerifyEmail and no route carries the verified middleware. That is fine for the website. For a mobile app that can be installed by anyone from a public store, I recommend gating mobile registration behind email verification (a soft gate: the account exists, but uploads are blocked until verified). It is a small change confined to the mobile controllers and does not alter web behaviour. Flag it as a decision — see §15.

08In-app purchase design

You chose native IAP on both stores with Stripe staying on the Laravel side. That is the right call for store approval, and it is the most intricate part of this project. The whole design hangs on one sentence:

A purchase made on a phone is a claim. It becomes an entitlement only after your server verifies it with Apple or Google, and the entitlement is written by the same PlanCatalog::applyToCompany() that Stripe already uses.

8.2 The entitlement precedence rule

EntitlementResolver::resolve(Company $company): array
{
    // 1. Stripe wins if it is live. It is the pre-existing source and
    //    the only one that can be Enterprise.
    if ($company->subscribed('default')) {
        return ['plan' => PlanCatalog::resolvePlanKeyForCompany($company), 'source' => 'stripe'];
    }

    // 2. Otherwise the newest non-expired store subscription.
    $store = $company->storeSubscriptions()
        ->whereIn('status', ['active', 'grace_period', 'billing_retry'])
        ->latest('expires_at')->first();

    if ($store) {
        return ['plan' => $store->plan_key, 'source' => $store->store];
    }

    // 3. Otherwise free.
    return ['plan' => PlanCatalog::defaultKey(), 'source' => 'free'];
}
The double-billing guard is not optional
Without it a customer can subscribe on the web and in the app and pay twice, which produces refund requests, chargebacks and — if a reviewer hits it — a rejection.
  • GET /billing returns can_purchase: false with managed_by: "stripe" when a Stripe subscription is active. The app then hides the purchase buttons and shows "Your plan is managed on banksheet.pro".
  • POST /billing/purchases/* returns 409 subscription_conflict if a Stripe subscription is active, before any store call.
  • The web BillingController::subscribe should refuse when an active store subscription exists and point to App Store / Play subscription management. this is the one place a web file might need a guard added

8.3 Apple — the flow that actually gets approved

  1. App Store Connect: one subscription group, four products, localised names/descriptions in at least English and Italian, a review screenshot per product, and a subscription privacy policy + terms link inside the app (Apple checks this).
  2. In the app: StoreKit 2 via the in_app_purchase plugin. Set appAccountToken to a UUIDv5 derived from company_id — this is what lets a server-to-server notification find the right tenant when no user is logged in.
  3. On purchase: send the signedTransactionInfo JWS to POST /billing/purchases/apple. The client does not decide anything.
  4. On the server: verify the x5c certificate chain up to Apple's root, check bundleId and environment, then call the App Store Server API for the authoritative renewal state. Never trust the JWS payload alone, and never call the deprecated verifyReceipt.
  5. Grant: upsert store_subscriptions keyed on (apple, original_transaction_id), then PlanCatalog::applyToCompany($company, $planKey, 'active'). Finish the transaction on the client only after your server returns 200.
  6. Notifications: configure App Store Server Notifications V2 → /webhooks/apple/asn. Handle SUBSCRIBED, DID_RENEW, DID_CHANGE_RENEWAL_STATUS, DID_FAIL_TO_RENEW (grace period), EXPIRED, GRACE_PERIOD_EXPIRED, REFUND, REVOKE. Deduplicate on notificationUUID.
  7. Restore: a visible "Restore purchases" action is required by 3.1.1. It re-verifies and re-grants.
  8. Sandbox: test with sandbox Apple IDs. Sandbox renewals are compressed (a month ≈ 5 minutes), which is how you test expiry and grace period in an afternoon.

8.4 Google — the flow that actually gets approved

  1. Play Console: subscriptions with base plans and offers; a Google Cloud service account granted "View financial data" + "Manage orders and subscriptions"; the JSON key on the VPS, outside the web root.
  2. In the app: Play Billing Library 9 via in_app_purchase_android. Set obfuscatedAccountId to a hash of company_id.
  3. On purchase: send purchaseToken + productId to POST /billing/purchases/google.
  4. On the server: purchases.subscriptionsv2.get → check subscriptionState and expiryTime → grant → acknowledge().
Google will refund the customer if you do not acknowledge within 3 days
This is the most common way a first Android IAP integration silently loses money. Acknowledge on the server, immediately after a successful grant, and add a nightly sweep that acknowledges anything missed.
  1. Notifications: RTDN → Cloud Pub/Sub → push subscription → /webhooks/google/rtdn. Verify the Pub/Sub JWT, deduplicate on messageId, and always re-query the Play API rather than trusting the notification body.
  2. Test: licence testers in Play Console get real purchase flows with test cards and accelerated renewals.

8.5 Where the money reconciliation lives

Nothing about Stripe changes. StripeWebhookController, SubscriptionLifecycleService and the two scheduled billing commands stay exactly as they are. The store path is a sibling, not a replacement, and both converge on the same three lines:

// Stripe path today — SubscriptionLifecycleService.php:38-72
$this->plans->applyToCompany($company, $planKey, $status);

// Store path tomorrow — StoreSubscriptionService

Build-vs-buy worth ten minutes of thought
Everything in §8.3–8.4 is roughly 2.5–4 weeks of backend work to do properly, plus ongoing maintenance as both stores evolve their APIs. A subscription infrastructure vendor (RevenueCat and similar) collapses that to a few days plus one webhook, at the cost of a third-party dependency in your billing path and a percentage fee above a free tier. Given that you are one developer maintaining three products, I would at least price it. If you buy, the EntitlementResolver and the double-billing guard in this plan stay exactly the same — only the two verifier classes are replaced.

9.4 Three implementation details worth deciding up front

a. Upload is the riskiest interaction on mobile

The server caps uploads at max:20480 (20 MB) in a single request DocumentController.php:63-70, and there is no chunked/resumable path. On a train, a 15 MB scan over a flaky connection will fail repeatedly. Mitigations, in order of value:

  • Compress client-side before upload — a camera scan should be rendered to a reasonable-DPI PDF, not a 40 MB photo bundle.
  • Enqueue uploads locally and retry with exponential backoff; show a persistent "3 pending uploads" state so nothing is silently lost.
  • Send an Idempotency-Key per upload — the server-side pattern already exists EnforceApiIdempotency.php:29-95, so a retried upload after a timeout will not double-charge quota. Note its known defect: the documented 24-hour TTL is not implemented, so keys are honoured forever. Fix that when you reuse it.
  • v2: a resumable upload endpoint (tus-style or a simple chunk API) if telemetry shows failures.

b. Replace polling with push as early as you can afford

Extraction takes 10–90 seconds by your own documentation Api/V1/DocumentController.php:23-30. Polling /documents/{id}/status every 3 s works and is what v1 should ship, but on mobile it drains battery and dies the moment the app is backgrounded. Firing an FCM message from ProcessDocumentJob's success path is a two-hour backend change with a disproportionate UX payoff. Put it in v1.1 at the latest.

c. Reuse the 13 existing locale files

You already have 13 key-aligned JSON catalogues with 1881 keys each. Write tool/gen_arb_from_laravel.dart to transform lang/{code}.json into l10n/app_{code}.arb and run it in CI. The mobile app ships fully localised from day one for free, and translations stay in one place. Note the caveat in config/locales.php:8-10: marketing pages are deliberately untranslated — that does not affect the app, which is all authenticated screens.
